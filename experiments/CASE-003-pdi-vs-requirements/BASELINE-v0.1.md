# CASE-003 — Baseline v0.1

The baseline is deliberately competent rather than a strawman.

It follows a conventional requirements-to-architecture workflow:

1. characterize the problem;
2. derive functional requirements;
3. derive quality/governance requirements;
4. identify constraints and assumptions;
5. derive architecture components;
6. attach trace links from requirements to components;
7. select resources;
8. record unresolved assumptions.

The baseline is allowed to preserve:
- provenance;
- temporal scope;
- authority;
- uncertainty;
- conflict;
- entities;
- relationships;
- consequences.

Therefore any PDI result that depends merely on preserving these fields cannot be interpreted as evidence of PDI-specific value.

The baseline fails only when the declared PDI procedure provides information or reproducibility that the competent baseline cannot obtain from the same problem information without adopting the PDI intermediate representation itself.
